This page outlines changes in the CGTv2 hardfork for node operators, bridges, indexers and other integrators of the native CELO bridge.

<Note>
CGTv2 activates when its L1 governance transaction executes, not at a set timestamp. Dates are TBD.

- Celo Sepolia testnet activation: TBD
- **Mainnet** activation: TBD
</Note>

## What is the CGTv2 hardfork?

The CGTv2 hardfork is a maintenance upgrade. It moves CELO, Celo's gas token, from the OP Stack's legacy custom gas token design to [Custom Gas Token v2](https://docs.optimism.io/op-stack/features/custom-gas-token) (CGT v2), the design that current OP Stack releases support. It adds no new features. It brings Celo in line with the OP Stack so that Celo can adopt future OP Stack upgrades.

Key changes include:

- **New CELO bridge**: CELO moves between Ethereum and Celo through a dedicated bridge, `CeloGasBridgeL1` on Ethereum and `CeloGasBridgeL2` on Celo, instead of through `OptimismPortal2` directly. The L1 CELO held by `OptimismPortal2` moves into `CeloGasBridgeL1`.
- **L1 contract upgrade**: The L1 contracts are upgraded to the OP Stack contracts that support CGT v2 ([op-contracts v6.0.0](https://docs.optimism.io/notices/archive/upgrade-18)).
- **L2 predeploys**: The upgrade installs the CGT v2 predeploys that hold and release native CELO for the bridge.
- **Bridging pause**: The system is paused for the upgrade. No withdrawal can be proven or finalized while it is paused, and `CeloGasBridgeL1` accepts CELO deposits only once the system is unpaused after the upgrade activates on Celo.

For the full technical specification, see the [CGTv2 upgrade spec](/operate/specification/upgrades/cgtv2).

## For bridges and users

Users and apps on Celo do not need to do anything, unless they have a CELO withdrawal to Ethereum in progress (see step 3 below). CELO stays the native gas token, and [token duality](/operate/specification/token-duality) is unchanged: the CELO ERC-20 on Celo shows the same balance as the native balance.

Bridges, exchanges and other services that move CELO between Ethereum and Celo through the native bridge must update their integration:

1. Deposits (Ethereum to Celo) approve `CeloGasBridgeL1` and call `CeloGasBridgeL1.deposit(address _to, uint256 _amount, uint32 _minGasLimit, bytes _extraData)` instead of `OptimismPortal2.depositERC20Transaction()`, which is removed.
2. Withdrawals (Celo to Ethereum) start with `CeloGasBridgeL2.withdraw(address _to, uint256 _amount, uint32 _minGasLimit, bytes _extraData)`, sending `_amount` as the transaction value, instead of `L2ToL1MessagePasser.initiateWithdrawal()`. Proving and finalizing still happen on `OptimismPortal2`, and `CeloGasBridgeL1` then pays out the CELO on Ethereum.
3. A CELO withdrawal started under the legacy design must be proven and finalized before the system is paused for the upgrade. `OptimismPortal2` rejects proving or finalizing withdrawals while the system is paused, and after the upgrade it rejects any withdrawal that carries CELO, so such a withdrawal cannot be paid out. Finalizing needs a proof and the challenge window (about 7 days on mainnet) first, so start any withdrawal well before the cutoff.

While the system is paused, `CeloGasBridgeL1` rejects deposits and no withdrawal can be proven or finalized. Other ERC-20 tokens keep using `L1StandardBridge` and `L2StandardBridge`. Contract addresses and the cutoff date for legacy withdrawals will be published on this page before the upgrade.

## For indexers and explorers

CELO bridging emits the standard bridge events `ERC20BridgeInitiated` and `ERC20BridgeFinalized` from `CeloGasBridgeL1` and `CeloGasBridgeL2`, with the L1 CELO token and the CELO ERC-20 on Celo as the token pair. Use these events for CELO amounts. The portal's low-level `TransactionDeposited` and withdrawal events still appear, because the bridge sends its messages through the portal.

At activation, the `NativeAssetLiquidity` predeploy (`0x4200000000000000000000000000000000000029` on Celo) receives a native balance of 1,000,000,000 CELO minus the amount moved into `CeloGasBridgeL1`. It pays out native CELO when CELO is bridged from Ethereum and takes it back when CELO is bridged to Ethereum. Supply trackers and explorers that sum native balances will see this balance.

## For node operators

Node operators will need to upgrade to the CGTv2 releases before the L1 governance transaction executes. The releases are TBD. For current versions see [Network config](/operate/operators/network-config).
